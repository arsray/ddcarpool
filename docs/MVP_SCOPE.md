# MVP 范围定义

本文档是 MVP 验收的单一事实来源。范围变更需 PR 更新本文档并经全员确认。

> **订单模型：** 与 [`DATA_MODEL.md`](./DATA_MODEL.md) v2 对齐 — P0 仅 **乘客发单** + **司机广场接单**；状态五态 `matching` → `pending_departure` → `in_progress` → `completed` / `closed`。

## 产品目标

内部同事在**固定点位**之间发布和接取蹭车/捎带需求，匹配后协调并完成行程。

## 用户路径（验收标准 · P0）

```
登录 → 浏览广场 → 乘客发布搭车单 → 司机接单 → （可选聊天 P1）→ 标记完成 → 在我的中查看
```

## P0 — 必须完成

### M1 登录 / Profile / 我的订单

- [ ] 微信云开发登录（获取 openid）
- [ ] 首次授权昵称与头像
- [ ] 「我的」页展示 Profile
- [ ] 「我的订单」列表（我发布的 + 我接取的）
- [ ] Mock 测试账号切换（Bob / Alice）

### M2 主页 / UI

- [ ] 全局设计 token（颜色、字号、间距、圆角）
- [ ] 共享组件：按钮、卡片、空状态、标签
- [ ] 主页（广场）：`matching` 订单列表 + 筛选
- [ ] Tab 导航：广场 / 发布 / 我的（`custom-tab-bar`）

### M3 订单生命周期 / 点位

- [ ] 乘客发布搭车单（起点、终点、出发时间、人数、备注 ≤100 字）
- [ ] 订单详情页
- [ ] 状态流转：`matching` → `pending_departure` → `completed`（Mock 可跳过 `in_progress`）
- [ ] 司机广场接单、标记完成
- [ ] 匹配中过期 → `closed`
- [ ] 点位数据：默认常量或云数据库 `points` 集合
- [ ] 顺路排序（`configured_routes` + `matchScore`）

### M4 聊天

- [ ] 仅 `pending_departure` | `in_progress` 订单可进入聊天（P1）
- [ ] 文字消息收发
- [ ] 消息按订单隔离（参与者仅乘客与司机）

## P1 — MVP 内建议完成

- [ ] 发布页表单项校验与错误提示（Mock 部分已实现）
- [ ] 订单卡片展示状态标签
- [ ] 下拉刷新列表
- [ ] `cancelOrder`、`startTrip`（完整三态闭环）
- [ ] 乘客/司机取消与关闭原因文案

## 明确不做（Post-MVP）

| 功能 | 原因 |
|------|------|
| 地图选点 / 导航 | 复杂度高，MVP 用固定点位 |
| 车主「发布行程」锚点单 + 匹配推荐副流程 | P2；P0 仅乘客发单 + 司机接单 |
| 订阅消息推送 | 可后续迭代 |
| 管理后台 | 点位先用常量或手动写库 |
| 语音 / 图片消息 | 聊天 MVP 仅文字 |
| 企业内部 SSO / 工号白名单 | 可 Phase 2 加 |

## 「路线」的定义（M3 必读）

MVP 中的路线 = **从固定点位列表中选择起点 A 和终点 B**，展示为 `A → B`。

不包含：地图 API、驾车路线计算、途经点优化。

## 「订单」的定义

**订单（Order）** = 一条乘客搭车需求（P0），对应数据库集合 `orders`（页面路由仍保留 `publish` / `detail` 命名）。

全项目统一使用 **订单** 一词，不再使用「需求」「request」作为对外术语。

## 验收 Checklist

集成测试时逐项勾选：

- [ ] 用户 A（乘客）发布搭车单 → 广场可见 `matching`
- [ ] 用户 B（司机）广场接单 → `pending_departure`，乘客收到通知
- [ ] 司机或乘客标记完成 → `completed`
- [ ] 过出发时间仍为 `matching` → `closed` + `expired`
- [ ] （P1）双方可进入聊天并收发文字
