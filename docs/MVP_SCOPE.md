# MVP 范围定义

本文档是 MVP 验收的单一事实来源。范围变更需 PR 更新本文档并经全员确认。

## 产品目标

内部同事在**固定点位**之间发布和接取蹭车/捎带需求，匹配后协调并完成行程。

## 用户路径（验收标准）

```
登录 → 浏览广场 → 发布或接取订单 → 匹配成功 → 聊天协调 → 标记完成 → 在我的中查看
```

## P0 — 必须完成

### M1 登录 / Profile / 我的订单

- [ ] 微信云开发登录（获取 openid）
- [ ] 首次授权昵称与头像
- [ ] 「我的」页展示 Profile
- [ ] 「我的订单」列表（我发布的 + 我接取的）

### M2 主页 / UI

- [ ] 全局设计 token（颜色、字号、间距、圆角）
- [ ] 共享组件：按钮、卡片、空状态、标签
- [ ] 主页（广场）：订单列表 + 类型筛选
- [ ] Tab 导航：广场 / 发布 / 我的

### M3 订单生命周期 / 点位

- [ ] 发布订单：求蹭车 / 可捎带
- [ ] 选择起点、终点（固定点位列表）
- [ ] 选择出发日期与时间
- [ ] 订单详情页
- [ ] 状态流转：待接取 → 已匹配 → 已完成 / 已取消
- [ ] 接取、取消、标记完成
- [ ] 点位数据：默认常量或云数据库 `points` 集合

### M4 聊天

- [ ] 仅「已匹配」订单可进入聊天
- [ ] 文字消息收发
- [ ] 消息按订单隔离（参与者仅发布者与接取者）

## P1 — MVP 内建议完成

- [ ] 发布页表单项校验与错误提示
- [ ] 订单卡片展示状态标签
- [ ] 下拉刷新列表

## 明确不做（Post-MVP）

| 功能 | 原因 |
|------|------|
| 地图选点 / 导航 | 复杂度高，MVP 用固定点位 |
| 顺路匹配 / 多人同车拼车算法 | 非核心验证目标 |
| 订阅消息推送 | 可后续迭代 |
| 管理后台 | 点位先用常量或手动写库 |
| 语音 / 图片消息 | 聊天 MVP 仅文字 |
| 企业内部 SSO / 工号白名单 | 可 Phase 2 加 |

## 「路线」的定义（M3 必读）

MVP 中的路线 = **从固定点位列表中选择起点 A 和终点 B**，展示为 `A → B`。

不包含：地图 API、驾车路线计算、途经点优化。

## 「订单」的定义

**订单（Order）** = 一条蹭车/捎带需求，对应数据库集合 `orders`（脚手架中页面路由仍保留 `publish` / `detail` 命名）。

全项目统一使用 **订单** 一词，不再使用「需求」「request」作为对外术语。

## 验收 Checklist

集成测试时逐项勾选：

- [ ] 用户 A 发布「可捎带」订单
- [ ] 用户 B 在广场看到该订单
- [ ] 用户 B 接取，订单变为「已匹配」
- [ ] 双方进入聊天互发消息
- [ ] 任一方标记完成
- [ ] 双方在「我的订单」中看到已完成记录
